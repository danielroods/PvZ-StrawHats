Architecture

Five layers, one clear rule: views stay dumb.

Every screen, animation, and button reads from the model — never the other way around. It's what let the whole graphical layer get built in Phase 2 without rewriting the game logic underneath it.

M

model/

Game state, entities, plants, zombies, levels, user data. The single source of truth.

V

view/

LibGDX screens, renderers, UI components, PAM-driven animation playback.

C

controller/

Input handling, game loop control, screen navigation and back-stack.

S

service/

Cross-cutting systems — JSON parsing, email, asset management.

N

net/

The embedded TA grading portal and account sync client/server.

Player input → controller/ → model/ → view/ renders the result
How It Got Built

Four phases, each one a different discipline.

Not four sprints of the same work — four genuinely different jobs, done in order, each one depending on the last.

01

Design

Mapped the full system before writing a line — entities, level types, chapter mechanics, and the model/view/controller boundaries that everything else had to respect.

02

Code

Built the terminal-driven core engine — plant and zombie logic, combat, waves, accounts, progression — with zero graphics, proving the rules before rendering a single pixel.

03

Graphics

Layered a full LibGDX view on top, screen by screen, changing as little of the model and controller as the spec allowed — animation, UI, and chapter identity, without touching the rules underneath.

04

Network

Added the systems that reach outside the game itself — the embedded TA grading server, account sync, and automated email confirmations.

Core Systems

Six systems doing the real work.

Presented here the way the game presents its own plants — every system gets its own packet, its own cost, its own reason to exist.

🌻

PAM Animation Engine

idle · attack · special states

A custom TextureBank / PamPlayer pipeline drives every plant and zombie's idle, attack, and reaction animation from a single opaque, reusable core.

🗺️

World Map & Stages

shared base, per-chapter variation

All four chapter maps inherit from one StagesScreen base — shared enums, shared logic, template methods for what each chapter does differently.

🎴

Collection & Cards

reused everywhere, built once

One SeedPacketCardFactory renders plant/zombie cards across the collection screen, the shop, and in-battle plant selection — zero duplicated UI logic.

⚔️

Combat & Armor

degrades visibly, dies loudly

Cone, bucket, helmet, newspaper, and knight's-shoulder armor types each track and visually reflect their own remaining health.

🎯

Boss Encounters

three phases, one very bad robot

Zomboss fights run a randomized attack cycle against a three-segment health bar, with a stagger window between each phase.

📧

TA Grading Portal

local server, real email

A standalone embedded HTTP server lets course TAs sign in, credit in-game currency, and trigger a styled HTML confirmation email automatically.

Field Notes

Bugs that taught the codebase something.

The unglamorous half of building this — four problems that only gave up their real cause after actually running the code, not reading it.

Runtime hang

The catch-up loop that never caught up

Vasebreaker would occasionally freeze the whole game. The cause was a fixed-timestep loop in GameScreen.render() with no upper bound — under load it tried to simulate more and more ticks per frame until the app effectively stopped. Fixed with a hard MAX_TICKS_PER_FRAME cap.

Silent logic bug

A sign that only broke under motion

The Jester zombie's deflection logic looked correct on paper — static analysis found nothing. Only running it revealed a Math.abs(speed.x()) call quietly discarding direction, sending deflected projectiles the wrong way every time.

Framework gotcha

The layout container that ate every click

Overlay UI stopped receiving touch input for no visible reason. Turned out Stack.add() in LibGDX silently forces every child to fill the entire screen on each layout pass — overriding manual positioning underneath it. Overlays moved to stage.addActor() instead.

Refactor

Four maps, one shared spine

Each chapter's world map screen started as its own copy-pasted class. Unified into a single StagesScreen base with shared enums and template methods — Dark Ages, the most visually divergent chapter, overrides only what it truly needs to.
